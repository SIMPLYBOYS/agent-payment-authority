> 2026-10-23，Claude Code。Aaron 10/23：「我們進行批次 2」。範圍是 `docs/commercial-gap-review.md` 的 B1 展示畫面、B2 可信度區、B3 白話用語、B6 交付與收據。

> 本文是提案，還沒有改程式；第 7 節的 GD1～GD5 要 Aaron 決定。

## 1 目標

觀眾只看一個畫面，就能跟上一筆購物從委託到交付的五步，並且在每一步看到「為什麼可信」的一個證據。主持人頁留在另一個螢幕操作，觀眾看不到按鈕、表格和代碼。

不在本批：第二位客人付款與一起開始（批次 3）、本人確認委託（批次 4）、一鍵啟動（批次 5）。本批的畫面要能在這些做完後直接沿用，所以從第一天就支援多位客人。

## 2 觀眾畫面 `/show`

投影用 16:9（1920×1080，也要能在 1280×720 讀）。最小字級 24 px，金額 48 px。

```
┌───────────────────────────────────────────────────────────────┐
│ 示範商店 · Base Sepolia 測試網路 · 測試 USDC（不是真錢）          │
├──────────────────────────────────────────┬────────────────────┤
│                                          │ 客人 A 的 Agent      │
│              Unity 商店場景                │ ① 委託   ✓          │
│        （客人、櫃台、交付區）               │ ② 選購   ✓          │
│                                          │ ③ 核准   ● 等本人核准 │
│   場景下方的中文字幕：                      │ ④ 付款              │
│   「Agent 想買 0.50 USDC 的簡報，            │ ⑤ 交付              │
│     超過自動範圍，正在等本人核准」            │                    │
├──────────────────────────────────────────┴────────────────────┤
│ 為什麼可信：委託 · 憑證 · 本人核准 · 預算預留 tx · 付款 tx · 收據    │
└───────────────────────────────────────────────────────────────┘
```

- **五步**：委託 → 選購 → 核准 → 付款 → 交付。每一步的狀態只有：未到、進行中、完成、未確認、失敗。顏色沿用 `docs/commercial-transaction-flow.md:224`：琥珀是等你處理，綠是已確認，藍是交付，紫是未知，紅是失敗。
- **每一步一句白話**，例如：
  - 委託：「客人交代 Agent：預算 5 USDC，超過 0.10 要問我」（E1-a 情境的數字）
  - 選購：「Agent 選了一份簡報，報價 0.50 USDC」
  - 核准：「在委託範圍內，自動放行」，或「超過自動範圍，等本人核准」，或「本人用手機和聲音核准了」，或「超出預算，已拒絕」
  - 付款：「先預留預算，再付款，兩筆鏈上交易」
  - 交付：「已交付，附收據」
- **多位客人**：右欄每位客人一張卡，各自的五步。現在只有一位客人付款，所以只會有一張；批次 3 起會有兩張。
- **未確認不演成功**：付款結果未知時寫「確認中」並用紫色；沒有交付就不演取貨（`docs/commercial-scenes.md:74`、`docs/commercial-demo-roadmap.md:103`）。

## 3 白話用語（B3）

觀眾畫面一律用白話；代碼、事件名稱、基本單位只留在主持人頁與證據抽屜。舉例：

| 現在 | 觀眾畫面 |
|---|---|
| `Allow`／`WITHIN_ALLOW_MAX` | 在委託範圍內，自動放行 |
| `Ask`／`HUMAN_APPROVAL_REQUIRED` | 超過自動範圍，等本人核准 |
| `Deny`／`INSUFFICIENT_BUDGET` | 超出預算，已拒絕 |
| `Deny`／`MERCHANT_NOT_ALLOWED` | 不在允許的商店，已拒絕 |
| `500000` | 0.50 USDC |
| `BUDGET_RESERVED` | 預算已預留 |
| `PAYMENT_SETTLED` | 已付款（鏈上已確認） |
| `RECEIPT_ISSUED` | 已交付，附收據 |
| `VOICE_PHRASE_MISMATCH` | 唸的內容不對，已拒絕 |

對照表放在 `web/adapter.js`，和現有的白話函式放在一起，單元測試逐項覆蓋；沒有對照的代碼寫「其他原因（主持人頁有細節）」，不直接顯示代碼。

## 4 可信度區（B2）

每一步對應一個證據，只寫已經有記錄支持的事：

| 步驟 | 顯示 | 可以點 |
|---|---|---|
| 委託 | 「委託內容由主持人代客人確認（示範）」：照實說是模擬，直到批次 4 | — |
| 憑證 | 「Agent 出示了客人的憑證，檢查通過（測試發行者）」：C2 的 BBS+ 結果 | — |
| 核准 | 自動放行，或「本人以已登記的裝置核准＋聲音相符」；virtual authenticator 照實寫 | — |
| 預算預留 | 「tx#1：預算預留（含 ZK 預算證明）」 | Base Sepolia 時連到 basescan |
| 付款 | 「tx#2：付款結算」，並註明「和 tx#1 是兩筆不同的交易」 | 同上 |
| 交付 | 「收據 rcpt-…，記錄了內容的 sha256」 | — |
| 獨立驗證 | 場次後由 checker 產生的 E1～E10 結果（見 GD4） | — |

不宣稱：
- 畫面不自行說「ZK 已驗證」或「通過」；這兩句只能來自 checker 的報告（`docs/commercial-e1a.md:125`、`docs/demo-presentation-design.md:275`）。
- 本機 anvil 不說成 testnet；virtual authenticator 不說成裝置；委託確認不說成本人。
- E1-a 標為 `not_evaluated` 的四項（BBS+ 重驗、語音 FAR／FRR、Admin 聚合、本人確認委託）不出現在「已驗證」裡。

## 5 交付與收據（B6）

- **網頁收據卡**：交付後在場景上方浮出收據卡，欄位照概念稿 `docs/mockups/commerce/3-receipt.html`：商品、金額、網路、核准方式、兩筆交易（標「不是同一筆」）、收據編號、內容摘要。gas 與模型用量不在本批。
- **Unity 交付**：現在 `ShopView.Station()` 把 `delivered` 直接送到出口（`ShopView.cs:121-131`），客人沒有經過交付區。改成：`paid` 走到交付區，`delivered` 在交付區停留約 2 秒後出店。Unity 的建置與測試用 `scripts/unity/unity.sh`（batch mode），由 Claude Code 執行。

## 6 資料怎麼到觀眾畫面

限制：token 只存在主持人頁的記憶體裡（`web/hostcreds.js:134-153`），觀眾畫面拿不到；每位客人的資料要用該客人的 viewer token 讀；checker 只輸出到命令列，報告存在 `var/`。

見 GD1、GD4。
