# 商業級 demo 落差盤點

> 2026-10-23，Claude Code。Aaron 10/23：「我觀察到，目前距離我們要的商業等級的 demo 其實還有不小的落差」→「先全部盤點」。Aaron 最在意的兩塊：**故事完整**（真人確認委託、多位客人同時購物並付款）與**畫面呈現**（觀眾看得懂、看得到「為什麼可信」）。
> 依據：三份唯讀調查（主持人的操作流程、觀眾看到的畫面、故事裡哪些是模擬），加上 E1-a 本機彩排與 Base Sepolia 實跑（10/23）的實際經驗。本文只盤點，沒有改程式。

## 1 結論

技術主線是通的：在 Base Sepolia 上，真實 Agent 的請購經本人裝置加語音核准後，以 ZK 預留、簽章、結算到交付，由 checker 向鏈查證通過（`docs/commercial-e1a.md` §6.2）。

但它還不是能上台的 demo，原因有三：
- **故事最前面的「客人委託」仍是主持人代按**，而且整場只有一位客人在付款。
- **沒有給觀眾看的畫面**：投影只能放主持人的操作頁，證據多半是代碼或藏在抽屜裡，checker 的結果完全不在畫面上。付款主機上還有幾處文字寫「不會付款」，和實際付款互相矛盾。
- **上台很重**：四個終端機、三個要 sudo、三組密語加配對碼；出錯沒有自動恢復，就緒表也看不到 Signer、relayer、語音的狀態。

## 4 上台順暢度

| # | 現況 | 補法 | 規模 |
|---|---|---|---|
| C1 | 每場要依序開四個終端機（語音服務、Signer、relayer、Host），三個用 sudo，三組密語加配對碼；語音模型載入要 2～3 分鐘 | 一個啟動腳本：依序啟動、等待各自的健康檢查、失敗時說清楚卡在哪；sudo 與密語由人輸入（安全上必須保留），但集中在一處 | 中 |
| C2 | 就緒表沒有 Signer、relayer、語音服務的狀態；服務停了只在核准時才發現 | 就緒表加這三列 | 小 |
| C3 | 彩排與實跑實際遇到：終端機被重用使服務停下、密語忘記、登記碼格式看不懂、重啟後憑證倒退、CLI 自動更新、語音唸錯被拒；都沒有自動恢復 | 主持人手冊（開場前檢查表、每種錯誤的處理）；頁面上出錯時直接寫下一步 | 小到中 |
| C4 | 每組實跑要手動建 host 目錄、換 task 標籤、記起點、查上限與餘額 | 併進 C1 的腳本：開場前自動檢查上限、餘額、task 未登記 | 小 |
| C5 | checker 查 Base Sepolia 要數分鐘到 20 分鐘；對帳要數分鐘 | 證據在場次後產生，展示時顯示「驗證中／已通過」；或預先跑好的那一場拿來展示 | 小（流程）＋B2 |

## 5 驗收收尾

- **E1-b 最終驗收**還沒做；E1-a 標為 `not_evaluated` 的四項：checker 重驗 BBS+ proof、語音的 FAR／FRR、Admin 聚合、委託由本人確認（A1 會解掉最後一項）。
- **M-D Admin 營運總覽**暫停中（`docs/commercial-md.md`）。

## 6 建議的順序

| 批次 | 內容 | 理由 |
|---|---|---|
| 1（立即，小） | B4 矛盾文字、B5 佔位與字級、C2 就緒表 | 成本低，卻直接影響可信度；之後每次彩排都受惠 |
| 2（核心） | B1 展示畫面、B2 可信度區、B3 白話用語、B6 交付與收據 | 你選的「畫面呈現」；這是觀眾真正看到的部分 |
| 3（核心） | A2＋A3：第二位客人的付款情境，兩位一起開始；付款依序處理，畫面照實說明 | 你選的「多位客人同時購物並付款」；大部分已有元件 |
| 4（核心） | A1 本人確認委託 | 你選的「真人確認委託」；牽涉信任邊界與 `/opt` 重新部署，先決定再做 |
| 5 | C1、C3、C4：一鍵啟動與主持人手冊 | 讓上台不依賴開發者在旁 |
| 之後 | A4 真正同時付款（先確認故事需要）、M-D、E1-b | |

批次 1～3 都能先在本機彩排；testnet 實跑照往例逐場核准。

留待之後（不在批次 1）：
- `adapter.js` 裡仍有幾處把核准寫成「已登記的裝置」（等你核准、`WEBAUTHN_APPROVAL`、裁決說明、已拒絕），它拿不到驗證器資訊；用 virtual authenticator 彩排時會說成裝置。
- `/api/mode`、`/api/viewer` 不帶憑證資訊：viewer 登入後，C2 主機的標章少了「C2＋」與「憑證 BBS+」。

- 主持人頁的幾處替換（live 警告、取消確認）依賴 `host.html` 的原字，沒有測試。
