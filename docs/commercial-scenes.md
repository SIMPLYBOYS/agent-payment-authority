## 1 一段話

商業 demo 從「一間商店」擴成**三個能操作的商務情境**：一個主場景承載完整交易閉環，另兩個是示範情境。三者走**同一套**委託 → 請購 → Policy／本人核准 → 付款 → 交付的狀態與事件，只換商品資料、Agent 的任務、場景佈置，以及由真實狀態驅動的演出。不另造付款流程。示範情境的商品與店家是示意資料，不能說成已接真 POS、庫存或物流；付款在 P2 前都不會發生。

## 3 三個情境（提案）

| | 資料研究室（主場景） | 街角咖啡（示範情境） | 巷口便利商店（示範情境） |
|---|---|---|---|
| 商務用途 | 數位資料／報告的購買 | 餐飲預訂與取餐 | 日常用品例行採買 |
| Agent | 研究助理 Agent（客人 A） | 午餐 Agent（客人 B） | 採買 Agent（客人 A） |
| 這次任務 | 買一份韓國市場簡報（0.50） | 訂 12:30 取餐的午餐套餐（0.08） | 補辦公室咖啡豆 ×2（0.36） |
| 你要決定 | 超過 0.10 的單筆要你核准 | 在範圍內自動通過，超過才問你 | 超過 0.10 要你核准；憑證被撤銷就自動關閉 |
| 交付（P2 之後） | 下載終端解鎖檔案 | 出餐口叫號 | 取貨櫃開格 |
| 空間分區 | 入口、報告書架（選購・報價）、櫃台・核准、下載終端（交付） | 入口、點餐看板（選購・報價）、櫃台・點餐、出餐口（叫號）、取餐區 | 入口、貨架（選購・報價）、冷藏櫃、櫃台・核准、取貨櫃（交付） |
| 資料來源 | 既有示意商店的 x402 報價；P2 接上測試網付款後才是真實閉環 | 示意菜單；沒有接 POS 或外送 | 示意商品；沒有接庫存或物流 |
| 主要示範的路徑 | Ask → 核准（模擬或本人裝置）→（P2）付款 → 下載 | Allow（範圍內）→（P2）付款 → 叫號 | Ask → 核准時憑證已撤銷 → 這筆已關閉 |

- **為什麼這三個**：派工建議由「既有資料商店、餐飲訂購、便利零售」出發，三者剛好涵蓋三種決策結果（要你核准、範圍內自動通過、失敗關閉）與三種交付（數位檔案、現場取餐、取貨櫃）。repo 裡沒有其他已核准的情境。
- **主場景用資料商店**：它是唯一已經有 x402 報價、能在 P2 走完真實測試網付款與數位交付的情境。現行的雜貨店外觀改為「報告書架＋下載終端」，讓觀眾看得出賣的是資料。

## 4 共用的狀態，而不是三套流程

- **相同**：委託、請購（同一個 `request_purchase` 工具）、Policy、本人核准（模擬或 A2 裝置）、憑證檢查（C2）、付款狀態、事件、證據抽屜、主持人頁的操作卡與「需要你處理」。
- **每個情境換的**：
  - 商品與報價（商店目錄的 product 與 x402 報價）；
  - Agent 的任務文字（場景目錄的委託用途）；
  - Unity 的場景佈置（分區、業務物件、角色走位）；
  - 交付區的演出（P2 之後，由真實的付款與交付事件驅動）。
- **資料面的最小改動**（給 UX3；本片不改程式）：
  - 場景目錄（`testdata/demo/scenarios-*.json`）每個 entry 加 `scene`（`data`／`cafe`／`mart`）；
  - 商店（`internal/merchant`）加兩組示意商品；
  - Host 把 `scene` 帶進 run 與頁面；
  - Unity 依 `scene` 載入對應佈置。

  委託、Policy、核准、付款與事件模型都不動。

## 5 場景動作 → 產品狀態 → 來源 → 查證 → 錯誤／未知

三個情境共用下表；各情境只差在「場景動作」那一欄的演出（見表下）。

| 場景動作 | 產品狀態 | 來源 API／事件 | 查證入口 | 錯誤／未知怎麼呈現 |
|---|---|---|---|---|
| 客人進場 | 委託已確認、Agent 開始 | `POST /api/sim/delegations`、`POST /api/host/runs`；事件 `TASK_STARTED`、`DELEGATION_BOUND` | 證據抽屜「事件鏈」 | 開始失敗：卡片顯示原因，客人不進場 |
| 走到選購區、看商品 | 選購與報價 | 工具呼叫 `list_products`、`get_quote`（無 Store 事件；真實執行可在查證面板看 trace） | 查證面板的工具呼叫 | 報價讀取失敗：停在選購區，不顯示價格 |
| 走到櫃台 | 請購已提出、憑證檢查 | `PURCHASE_PROPOSED`、`CREDENTIAL_VERIFIED`（v2） | 證據抽屜「憑證檢查」「intent_hash」 | 憑證未通過：Deny，帶理由離開 |
| 櫃台等待／通過／離開 | Policy 裁決：Ask／Allow／Deny | `POLICY_DECIDED`；`GET /api/tasks/{id}` 的 decision | 證據抽屜「裁決」「原因」 | Deny：顯示理由碼與白話說明，離開 |
| 「需要你處理」 | 單筆核准中 | `APPROVAL_SESSION_OPENED`；`GET /api/sim/approvals` 或 `GET /api/approvals` | 核准面板的摘要與 intent | 期限以後端為準；到期、撤回、作廢各有文字 |
| 核准或拒絕 | 已核准／已拒絕／已關閉 | `APPROVED`＋`GRANT_ISSUED`、`APPROVAL_DENIED`、`APPROVAL_WITHDRAWN`（含 `closed_reason`） | 證據抽屜「收尾」「grant」 | 憑證理由的關閉寫「憑證已撤銷（狀態無法確認、已過期），這筆已關閉」，不寫成 task 取消 |
| 走到付款／交付區 | 付款中、已付款、已交付 | **P2 之前沒有**：`payment_status=not_enabled` | 證據抽屜「付款」「交付」 | 一律顯示「付款未啟用，不會交付」；不演取貨、叫號或開格 |
| 卡住、斷線 | 未知 | 頁面讀取失敗、Unity 未回報 | 頁首連線狀態 | 顯示「未確認」，不把未知當成功 |

- **各情境的演出差異**：
  - 資料研究室：選購＝在報告書架看目錄；交付＝下載終端亮起；
  - 街角咖啡：選購＝看點餐看板；交付＝出餐口叫號、到取餐區；
  - 巷口便利商店：選購＝在貨架比價；交付＝取貨櫃開格。
- **標示**：示範情境的頁首多一個「示範情境：商品為示意資料」標籤，證據抽屜多一列「情境」寫明資料來源。主場景在 P2 前同樣標「付款未啟用」。

## 7 桌面與手機

- **桌面（1440×900）**：完整互動；左側場景與進度、右側需要你處理、Agent 卡與剛剛發生。
- **手機（390 寬）**：單欄；場景畫布縮小在上，進度只留步驟名，下方是核准卡。可以查看與做模擬核准；本人裝置核准（A2）在手機上排到後期（Touch ID、Safari、手機已延後），**不能用桌面截圖推定手機觸控驗收**。窄版不顯示上方的畫面切換，改由情境卡進入。

## 9 UX3 的最小實作拆分（建議）

1. **資料**：場景目錄加 `scene`；商店加兩組示意商品（咖啡店菜單、便利商店商品），只在 fake 目錄；Host 把 `scene` 帶進 run 與 `/api/host/runs`。
2. **網頁**：情境選擇畫面；頁首「示範情境」標籤；證據抽屜「情境」列；核准摘要「交付方式」列；進度列五步固定。沿用現有的狀態與文字函式（`web/adapter.js`）。
3. **Unity**：一個場景、三種佈置（依 `scene` 切換分區與業務物件），沿用現有 SceneRules 的 phase；交付區只在 P2 的交付事件後才演出，P2 前固定顯示「付款後才交付」。
4. **素材**：匯入第 8 節的主題單品，更新清單與 sha256。
5. **驗證**：每個情境一條瀏覽器檢查（現有 `c2-ui.mjs` 的模式），加上手機窄版截圖。

不做：真 POS、庫存、物流、NPC 尋路、通用遊戲引擎、影片。
