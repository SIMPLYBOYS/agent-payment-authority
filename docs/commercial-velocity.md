# Policy 的頻率限制（velocity）

> 2026-11-04，Claude Code。Aaron 11/3：「就依照這個順序把剩下的功能做完」的第 5 項，也是 A 階段的最後一項；做完就不再加功能（Aaron 11/4 同意 A～D 的方向）。FUTUREMODE 筆記列的確定性檢查有五項：task、asset、network、expiry、**velocity**，前四項都有了。
> **Aaron 11/4 的決定：不做，列進 D（下一期）。** 先前「照建議」（Z1～Z4 A）之後，查程式發現第 1 節的更正與 Z4 做不到；再看過長期的負面影響（第 7 節）後改為不做。屆時 Host 的 Policy 與 Signer 一起做。

## 1 現況

| 限制 | 在哪裡 | 擋的是什麼 |
|---|---|---|
| `allow_max`（城鎮 0.10） | Host 的 Policy | 單筆超過就改成 Ask，要本人核准 |
| 任務預算（城鎮 1.50） | Policy，加上鏈上的 ZK 預算合約（tx#1 預留） | 一個 task 的總額 |
| 委託的累計上限 | Signer | 一個委託總共簽過多少錢 |
| 核准人 24 小時上限 | Signer | 本人核准的累計金額 |
| relayer 每日 12 筆 | apa-relayer | tx#1 的筆數 |
| 商店每日上限 | 商店／apa-facilitator | tx#2 的筆數 |
| **一段時間內最多幾筆** | **沒有** | — |

缺口：在自動範圍內連續小額購買，Policy 只靠任務預算擋。**更正（11/4，查程式後）**：在這個展示裡，同一個 task 對同一件商品只會成立一筆請購（`toolbridge.PurchaseOrderID` 是 `po-<task>-<商品>`，重複請購只回報同一筆），每個 task 也只看得到自己場景的商品（書店三件，自動範圍內的只有講義）。所以單一 task 能成立的請購受限於場景的商品數；頻率上限擋的是**跨 task 的累積**（同一位客人被重新開始很多次、多個 task），以及商品很多的真實商店。testnet 上還有 relayer 和商店的每日筆數上限，但那兩道是保護測試額度用的：一旦用完，那一天所有人都不能再付款，而且是付款步驟才擋，不是 Policy 的判斷。另一種情況是一直送超過範圍的請購：每一筆都是 Ask，家長的手機就會一直跳核准請求。這就是「核准疲勞」：讓人習慣性按下同意（OWASP ASI09，人被 Agent 操縱）。

## 2 做法

**在 Host 的 Policy 判斷**，跟其他確定性檢查放在一起：
- 新的 Deny 原因：`VELOCITY_LIMIT`。
- 在付款之前就擋下，沒有 tx#1、沒有預留，錢沒有動。
- 事件、頁面、證據包都看得到這個原因。

- Policy 仍然是純函式。由 Store 在同一個交易裡查出「這位客人最近 W 秒內已經被判 Allow 或 Ask 的請購有幾筆」，連同其他可信狀態一起交給 Policy。
- 設定放在 profile：`velocity: { max: N, window_seconds: W }`。沒有設定，就不檢查，舊的 profile 照舊。
- 判斷的順序：前面的 Deny 檢查（設定、資產、商店、時效、預算）之後，判 Allow 或 Ask 之前。
- 頁面上的文字：「短時間內請購太多次，已拒絕」。
- 為什麼不放在 Signer：Signer 在 tx#1（預算預留）之後才簽 tx#2。在那裡擋的話，鏈上已經有一筆預留，畫面上是「預算已預留，但付款沒有送出」，觀眾看不懂。Signer 另外加一道備援，列為下一期（第 6 節）。

## 3 規模

| 切片 | 內容 | 驗證 |
|---|---|---|
| V1 | profile 的 `velocity` 欄位與驗證；`policy.Rules` 多一個輸入（最近的筆數）與 `VELOCITY_LIMIT`；`paycontract` 的原因代碼、schema、頁面文字 | Go 測試、頁面測試、契約向量 |
| V2 | Store 在決定的同一個交易裡算出最近的筆數（跨這位客人的所有 task） | Store 測試：剛好 N 筆、第 N+1 筆、窗口過了、別位客人的不算 |
| V3 | （看 Z3）一個 fake 的模擬情境：被誘導的 Agent 連續請購，第 N+1 筆被擋 | 瀏覽器檢查 |
| V4 | 併進 B 的 testnet 彩排 | 真實 Agent 正常購買不會碰到上限 |

## 4 要 Aaron 決定

| # | 問題 | 建議 |
|---|---|---|
| Z1 | 算哪些請購 | **A**：被判 Allow（會自動付款）或 Ask（會去問本人）的都算。兩種風險都擋得到：連續自動付款，以及一直跳出核准請求。被 Deny 的不算，因為它們不會付錢，也不會打擾人。**B**：只算 Allow。**建議 A** |
| Z2 | 範圍 | **A**：同一位客人的所有 task、所有店一起算，也就是「孩子的 Agent 不管去哪間店，十分鐘內最多幾筆」。**B**：每個 task 各自算。**建議 A** |
| Z3 | 數字 | **A**：十分鐘內最多 5 筆。城鎮裡每位客人最多 3 筆（三間店各一筆），再留 2 筆給重新開始。**B**：十分鐘內最多 3 筆，比較嚴，但重新開始一次就可能碰到。**建議 A**；本機與 testnet 用同一組 |
| Z4 | 要不要讓觀眾看到 | **A**：加一個 fake 的模擬情境（同「被誘導的 Agent」那種）：被誘導的 Agent 連續請購同一份 0.06 講義，第 6 筆被擋，「短時間內請購太多次，已拒絕」。只在本機 fake 主機。影片要不要用，錄影時再決定。**B**：只做測試，畫面上看不到。**建議 A** |

**Z4 A 做不到（11/4 更正）**：同一份講義在同一個 task 裡只算一筆，而一個 task 只買得到自己場景的商品，所以一個 fake 情境湊不出 6 筆。要在畫面上看到，只剩兩種做法：主持人在十分鐘內把同一位客人重新開始 6 次（操作笨重）；或替某個場景加一批便宜的示意商品（live 城鎮的真實 Agent 也會看到，等於改了商店）。重新提給 Aaron 決定。

## 5 界線

- 跟其他 Policy 檢查一樣，在 Host 的 Policy 執行。Host 被攻破的話，這一道也就沒了：Signer 的金額上限照舊，但沒有頻率限制。這一點寫進照實說的限制。
- 只算筆數，不算金額；金額由任務預算和 Signer 的累計上限負責。
- 改了 Policy 的判斷和原因代碼：`apa.pay.v1`、`v2` 的原因清單多一個值，舊的證據包仍然有效，契約版本號不變。

## 6 下一期（不做）

- Signer 另外加一道頻率上限（委託在一段時間內最多簽幾筆），當作 Host 被攻破時的備援。要改 Signer 並重新安裝到 `/opt`。

## 7 為什麼不做（Aaron 11/4）

看過的長期負面影響：
1. **可能擋到正常的展示**：彩排與錄影常重新開始，同一個資料庫裡先跑過的 fake 場次也算在內，十分鐘內第 6 筆就會在現場被擋。
2. **安全上的說法有缺口**：只放在 Host，也就是 Agent 直接連線的那個程式，Host 被攻破就沒了；Signer 沒有頻率上限。
3. **觀眾看不到**：只有測試，畫面與影片都看不到。
4. **契約多一個原因代碼**：頁面、Unity（字型與建置）、checker、向量都要一直同步。
5. **計數的語意有邊角**：被家長拒絕的 Ask 也算一筆。
6. **testnet 設定要另外寫進新場次**；以及時間成本。

在這個展示裡，單一 task 能買的筆數本來就受限於場景的商品數（第 1 節），做了擋不到實際的風險，卻多了現場被誤擋的可能。下一期要做時，Host 與 Signer 一起做，說法才完整。照實說的限制已更新（`docs/architecture.md`）。
