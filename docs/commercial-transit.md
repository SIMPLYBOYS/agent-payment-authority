# 地下鐵閘門自動扣款

> 2026-11-09，Claude Code。Aaron 11/9：「我希望能夠的客人移動的過程中就啟動交易的功能，而不一定需要像 hotel 那樣進門之後有特定的介面在進行交易，這次特別針對是通過地下鐵閘門的時候，能夠啟動自動扣款的交易場景」。
> Aaron 11/9 已決定：Policy 一核准閘門就開（結算在背景）；進站收一次固定車資、出站免費；先做閘門，之後再做領取 USDC 的場域（testnet 用真的 Circle faucet，見 §8）；限制照真實情況：「實際情況是有多少錢就花多少，不能花就隔天再花」。§6 的 R1～R4：「照建議」。

## 1 一段話

客人開通一次「捷運自動扣款」（本人確認一份捷運委託），之後每次走進站的閘門，Host 就替這份委託送出一筆車資請購，交給 Policy 判斷：准就開閘、頭上顯示扣款，鏈上結算在背景完成；擋下就不開閘，顯示是哪一個限制。每一趟都不呼叫模型，也不用本人再確認。

## 2 現況：為什麼不能直接用「開始一場交易」

- 交易都是一場 run：配一個登錄任務（`store.AcceptRun`）、本人確認一份委託、Agent（fake 腳本或真實 CLI）跑工具，`cmd/demo/control.go:236`。
- 委託綁定一個任務之後就不能再用（`internal/store/pay.go:214` 的 `DELEGATION_UNAVAILABLE`）；同一個任務對同一件商品只成立一筆請購（`toolbridge.PurchaseOrderID`，`po-<任務>-<商品>`）。
- 一位客人同時只能有一場 run（`c.active` 依客人記），整個 Host 最多 2 場。
- testnet 上每個新任務要一筆 relayer 的登錄交易，每位客人的登錄任務只有 5 個（`registry-e1a.json`）。

每趟都開一場 run 的話：每趟要本人確認一次委託（不是自動扣款），會擋住同一位客人在店裡的交易，testnet 幾趟就用完登錄任務。所以閘門另外做一個「捷運通行」，不改 run 的規則。

## 3 做法

### 3.1 捷運通行（一次授權）

- 第一次走到進站閘門時，閘門關著，提示「開通捷運自動扣款」；網頁照現在的委託確認方式（模擬，或本人用裝置）確認一份捷運委託，Host 開一個捷運任務綁上它。之後的閘門都自動扣。
- 捷運任務不是 run：沒有 Agent 程序，不佔「一位客人一場」與「最多 2 場」的名額，客人照常可以進店交易。一位客人一個，重設或 Host 停止時結束；額度用完、委託到期也就扣不下去。
- 委託沿用 Host 的 profile 與現有的檢查（預算、單筆上限、商店、到期）；捷運委託的預算 0.20（10 趟），單筆上限 0.02（就是一趟的車資：比它貴的不會自動付）。
- **一次拒絕就停用**：付款合約的規則是一筆 Deny 結束整個任務（`paycontract.Ended`，Agent 的任務也一樣：被拒之後不再自動付任何錢）。所以車資被擋下時，這張捷運通行就結束了，下一次走到閘門要本人重新開通（新的委託、新的任務）。被擋之前已經核准的車資，送到 relayer 的照常付完；還沒送出的停在「未付」（`not_paid_ended`）。
- 任務的事件照實標來源：捷運任務沒有 Agent（run conditions 的 agent 是 `none`），車資請購的 `PURCHASE_PROPOSED` 標 `fixture/host`，不是 `fake_cli` 或 `live_cli`。
- 預算在付款開始時才扣（BUDGET_RESERVED）；Policy 看的是剩下的預算。所以連續兩趟之間若上一趟還沒開始付款，第 11 趟可能先被核准、付款時才因超過預算失敗（紀錄照實寫）。

### 3.2 過閘門

1. Unity：客人走進進站閘門的通道口時停下（桿子放著），回報 `gate`（站名）。出站方向不收費，閘門直接開。
2. 網頁：收到 `gate`，呼叫 Host 的車資端點；回覆後送 `Gate {station, open, text}` 給 Unity。
3. Host：替捷運任務送出一筆車資請購（`subway-fare`，0.02），請購編號帶趟數（`po-<任務>-subway-fare-<n>`），在同一個交易裡回答 Policy 的結果。之後跟店裡的 Allow 一樣：`payflow.Starter` 接手，tx#1（預算預留）→ Signer 簽 → tx#2（商店結算）→ 收據。
4. Unity：准就抬桿、綠燈，客人頭上浮出「自動扣款 0.02」，通過；擋下就紅燈、桿子不動，浮出原因，客人可以轉身離開。

Unity 只顯示，照舊不做決定：開不開閘由網頁依 Host 的回答決定。沒有接 Host 的頁面（影片、只看畫面）不送「閘門啟用」，閘門維持現在的樣子，任何人都能通過。

### 3.3 擋下的情況（照真實的限制，不另開例外）

| 原因 | 誰擋 | 什麼時候恢復 |
|---|---|---|
| 頻率限制（600 秒 5 筆，同一位客人所有任務一起算） | Host Policy（有設時）、Signer | 時間窗過了 |
| 捷運委託的預算用完 | Host Policy | 重新開通（本人再確認一份） |
| 委託到期 | Host、Signer | 重新開通 |
| Signer 委託的累計上限（testnet `dlg-ta`／`dlg-tb` 1.00） | Signer | 換新的委託（Aaron） |
| 錢包餘額不足 | 結算時 | 有人轉錢進來（§8 的場域） |
| 商店、relayer 當日上限 | 商店／facilitator、relayer | 隔天（UTC） |

閘門依 Policy 的回答開。Policy 之後才會碰到的限制（Signer、餘額、當日上限）讓已經開過閘的那一趟付款失敗，紀錄上照實寫「車資未付」，像真實的捷運欠費。本機的 Host profile 沒有頻率限制、Signer 有（5／600 秒），所以本機第 6 趟會是「開閘、之後付款失敗」；見 §6 R3。

### 3.4 畫面

- 閘門：開著的那道桿子收起（綠燈），關著的放下（藍燈）；扣款中與擋下用頭上的泡泡說明，不另做介面。
- 網頁：捷運任務在紀錄裡是一列「捷運自動扣款」，每趟一張卡：趟數、站名、0.02、核准 → 預留 → 簽署 → 結算（tx 連結）→ 收據；擋下的寫原因代碼與中文說明。

## 5 界線

- 不改 run、店內交易、Policy 規則、Signer 與付款流程；捷運只是另一種「誰送出請購」。
- 不呼叫模型；車資的金額與商店都是 Host 的資料，網頁與 Unity 只傳站名。
- checker（`verify-demo`）這一輪不認得捷運任務；車資在 Store 的事件、鏈上與收據裡都查得到，checker 之後再補。
- testnet 每趟：一筆 relayer（tx#1）、一筆商店結算（tx#2）；開通一次：一個登錄任務、一筆登錄交易。都算進當天的上限。
